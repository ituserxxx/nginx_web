# 2026-08-31

## 项目扫描

nginx_web 是一个前后端分离的 nginx 检测控制台。后端 Go 单文件（server/main.go，
零第三方依赖，3 个 API：/api/hello、/api/nginx、/api/nginx/available），
前端 Vue 3 + Vite 8 + ant-design-vue（源码仅 App.vue / main.js / style.css）。
功能只做「检测」，没有配置文件管理等写入能力。

## WSL 启动适配改造（用户要求：只改代码，不代为执行）

用户环境：Windows 宿主机 + WSL2 Ubuntu 22.04，项目位于 /mnt/d/DDD/xxx/code/nginx_web。
用户明确要求自己手动跑，本次未启动任何服务。

### 定位到的三个真实阻塞点

1. **WSL2 端口冲突**：Windows 侧 PID 19848 监听 0.0.0.0:8080，WSL2 的
   localhostForwarding 会导致 WSL 内 bind 失败，表现为
   `listen tcp :8080: bind: address already in use`，但 WSL 内 `ss` 查不到占用者。
   原脚本用 `fuser -k` 清理端口，Ubuntu 22.04 默认无 psmisc，且清不掉 Windows 侧进程。
2. **git autocrlf=true**：会把 start.sh 转成 CRLF，WSL 下报 bad interpreter。
3. **平台原生二进制**：web/node_modules 只含 @rolldown/binding-linux-x64-{gnu,musl}，
   无 win32 版本 —— 依赖是给 WSL 装的，前端只能用 WSL 原生 node 跑，
   用 Windows node.exe 会报 "Cannot find native binding"。
   原脚本仅判断 vite.js 是否存在，误在 Windows 下 install 过就会误判为依赖齐全。

### 改动

- `start.sh` 重写：环境拦截（Windows Git Bash 直接退出）、端口探测多级回退
  （ss/lsof/fuser）、Windows 侧端口检测（netstat.exe，一次拉取缓存）、
  端口自动避让、setsid 进程组管理（可清 esbuild 子进程）、启动后 HTTP 健康检查、
  restart/status/help 子命令、need_reinstall 平台校验、彩色日志。
- `web/vite.config.js`：proxy target 改读 `API_PORT`（默认 8080）并用 127.0.0.1
  避免解析到 ::1；支持 `VITE_POLL=1` 开启轮询监听（/mnt 下 drvfs 不支持 inotify）。
- `server/main.go`：加请求日志中间件、SIGTERM 优雅关闭、PORT 合法性校验、
  bind 失败时给出 WSL 端口冲突的明确提示。gofmt / go vet / go build 均通过。
- 新增 `.gitattributes`：锁定 *.sh 等为 LF，覆盖 core.autocrlf=true。
- `README.md`：新增 WSL 排障章节（端口冲突、CRLF、HMR 失效、node 互操作）。

### 验证方式（未启动服务）

### 关键坑：版本比对

两个接口版本格式完全不同，必须归一化后比对：

- `/api/nginx`            -> `nginx/1.24.0`
- apt madison / dnf / apk -> `1.24.0-2ubuntu7.1` / `1.24.0-1.el8` / `1.24.0-r6`
- 带 epoch                -> `1:1.24.0-1`

`normalizeVersion` 正则必须写成 `/\d[\w.:+-]*/`（**要含冒号**），
否则 `1:1.24.0-1` 会在冒号处截断成 `1`。之后去掉 epoch 再取 `^\d+(\.\d+)*`。
`nginx -v` 取不到版本时后端返回字符串 `unknown`，归一化后为空串，已覆盖。

补充体验：已装版本不在列表（源码编译安装）时显示解释性提示，
否则会出现「已安装 1 个」但列表全为「未安装」的困惑。

## 可复用：不启动服务验证 Vue 组件（重要）

本机 Windows 无法运行 vite（node_modules 只有 linux 版 rolldown binding），
所以前端改动无法靠 dev server 验证。用下面两招替代，效果很好：

1. **编译验证**：node 直接 require `@vue/compiler-sfc`（项目已装），
   依次调 `parse` -> `compileScript` -> `compileTemplate`，
   compileTemplate 传 `bindingMetadata: script.bindings` 才能校验模板变量。
   任何模板语法错误、未定义变量都会暴露。

2. **端到端逻辑验证**：用正则从 .vue 抽出 `<script setup>` 内容、剥掉 import 行，
   再用 `new Function('ref','computed','onMounted','fetch', body + 'return {...}')`
   注入极简 mock（ref = `{value:v}`，computed = getter，onMounted 空实现，
   fetch 按 URL 返回构造好的响应），然后 await 调用组件的 detect() 等方法，
   断言 computed 结果。这样能跑真实组件代码而非复制品。

注意：测试脚本要写成 .cjs 文件再用 node 执行，别用 `node -e "..."`，
脚本里若含单引号会与 shell 引号冲突导致 unexpected EOF。
Git Bash 缺 file / chmod / sleep；rm -rf 会被 safe-delete 拦截，
清理临时文件改用 node fs.rmSync（虽报 trash 失败但实际已删除）。

## 排查：available 接口只返回 2 个版本

用户疑问：「/api/nginx/available 怎么只有 2 个，其他版本呢？」

结论：**不是 bug，是 Ubuntu 官方源的特性**。Ubuntu LTS 会冻结软件包的大版本，
只 backport 安全补丁，不提供历史版本。jammy(22.04) 的 nginx 固定为 1.18.0 系列：

```
nginx | 1.18.0-6ubuntu14.3 | ... jammy-updates/main amd64 Packages
nginx | 1.18.0-6ubuntu14.3 | ... jammy-security/main amd64 Packages   <- 与上一行同版本
nginx | 1.18.0-6ubuntu14   | ... jammy/main amd64 Packages
```

updates 与 security 两个源版本号相同，dedupe 后正好剩 **2 个**。
想看更多版本需要添加 nginx.org 官方源（该源有 1.20~1.28 等几十个版本）。

### 验证方式

把 apt/dnf/apk 三个解析逻辑从「调命令」里抽成纯函数
（`parseAptMadison` / `parseDnfList` / `parseApkPolicy`），
新建 `server/main_test.go`，用真实命令输出做断言，共 7 个测试全部 PASS：

- Ubuntu 官方源 3 行 -> 2 个版本（复现用户现象）
- nginx.org 源 5 行 -> 5 个版本（证明不丢版本）
- 过滤 libnginx-* / nginx-core 等无关包
- 空输出、无匹配行、epoch 版本原样保留、dnf、apk

抽取纯函数是必要的：原来 aptVersions 直接调 runCmd 执行外部命令，无法单测。

## 新增功能：源码编译安装 nginx

需求：在「未安装」行后加「立即安装」按钮，按用户给的步骤编译安装到 /usr/local/nginx，
源码放 /data/soft，并配置 config.d 站点目录后 reload。

### 三个必须解决的技术障碍

1. **vim 无法程序化执行**：原步骤里有 `vim nginx.conf` 手动编辑。
   改为 `ensureConfigInclude()` 程序化改写：mkdir config.d，
   再用 `strings.LastIndex(content, "}")` 定位 http 块结束符，在其前插入
   `include config.d/*.conf;`。幂等（已含 config.d 则跳过）。
2. **编译耗时 5~15 分钟，同步请求必超时**：做成异步任务。
   POST /api/nginx/install 立即返回 taskId，前端每 2 秒轮询
   GET /api/nginx/install/status?taskId=。任务表是内存 map + mutex，
   同一时刻只允许一个 running 任务。
3. **命令注入风险**：版本号来自前端且会拼进下载 URL 与命令参数。
   `coreVersion()` 用正则只提取数字版本段（天然剥离 `;` `&&` `$()` 等），
   再用 `strictVersionRe`(`^\d+\.\d+\.\d+$`) 二次校验，双重保险。

### 实现要点

- 后端 `installTask` 用 `exec.StdoutPipe/StderrPipe` + bufio.Scanner 双 goroutine
  流式收集日志，logf() 加锁并限制最多 5000 条防内存膨胀。
- **installTask 含 sync.Mutex，序列化必须走单独的 installTaskView 快照**，
  否则 go vet 会报 "passes lock by value"。
- 步骤拆成切片循环（准备目录→装依赖→下载→解压→configure→make→make install
  →校验启动→config.d+reload），任一步失败即记录中文原因并终止。
- `make -j$(nproc)` 的 `$(nproc)` 在 Go 里无法展开，改用 `runtime.NumCPU()`。
- apt-get 加 `DEBIAN_FRONTEND=noninteractive` 环境变量避免交互卡住。
- 下载用 wget，缺失时回退 curl，两者都没有则返回明确错误。
- 前端：a-popconfirm 二次确认（说明 root 权限与耗时风险）→ 弹窗展示实时日志
  （watch + nextTick 自动滚底），成功后自动 detect() 刷新列表；
  关闭弹窗只停前端轮询，不中断后端任务。

### 验证

后端新增 5 个测试（共 12 个）：coreVersion 10 例、注入防护（含
`; rm -rf /`、`$(reboot)`、`1.24.0 && curl ...` 等）、ensureConfigInclude
（写入位置在 http 块内 + 幂等 + 文件不存在报错）。全部 PASS。
前端 4 个场景：安装成功自动刷新列表、后端拒绝不轮询、中途失败跳过刷新、
进行中 installRunning 生效。全部 PASS。

## 修复：OpenSSL 3.0 下编译 nginx 失败

用户实测报错：
```
src/event/ngx_event_openssl.c:3993: error: 'HMAC_Init_ex' is deprecated:
  Since OpenSSL 3.0 [-Werror=deprecated-declarations]
src/event/ngx_event_openssl.c:5124: error: 'ENGINE_by_id' is deprecated
src/event/ngx_event_openssl.c:5132: error: 'ENGINE_set_default' is deprecated
```

根因链：
1. nginx 的 auto/cc/gcc 里硬编码了 `-Werror`（警告即错误）
2. OpenSSL 3.0 把 HMAC_Init_ex / ENGINE_by_id / ENGINE_set_default / ENGINE_free /
   SSL_CTX_load_verify_locations / ERR_peek_error_line_data 标记为 deprecated
3. nginx 1.24.0 及更早版本仍调用这些接口
4. deprecation 警告被 -Werror 升级为错误 -> ngx_event_openssl.c 编译中断

Ubuntu 22.04 自带 OpenSSL 3.0.2，所以只要编译旧版 nginx 就必踩。
nginx 官方 ticket #1964（Maxim Dounin 回复）给出的官方建议就是加 --with-cc-opt。

修复（两处）：

1. configure 追加 `--with-cc-opt=-Wno-error=deprecated-declarations`。
   注意用 `-Wno-error=` 而不是 `-Wno-`：前者保留警告可见（日志里仍打印）、
   只是不判为错误；后者直接不产生警告，排查时看不到线索。
2. 解压源码前先 `os.RemoveAll(srcPath)`：上次编译失败会留下 .o 与 Makefile，
   不清理的话重跑会再次失败。

把 configure 参数抽成 `configureArgs()` 函数，并加测试
`TestConfigureArgsIncludeOpenSSL3Compat` 防止该兼容选项被后续改动误删。
后端测试增至 12 个，全部 PASS。

## 新增：卸载功能（在「已安装」行加卸载按钮）

需求：在已安装行后面新增一个卸载按钮，停止 nginx 后卸载本工具编译安装的部分。

### 设计与实现

- 复用 install 的异步任务框架：`run()` 按 `Action` 字段分发到 `runInstall()` /
  `runUninstall()`。新增常量 `actionInstall`/`actionUninstall`（之前会话已建好常量与
  `Action` 字段，本次补齐逻辑）。
- `runUninstall()` 步骤：
  1. 停止 nginx：优先 `/usr/local/nginx/sbin/nginx -s stop`，再 `pkill -x nginx` 兜底，
     两步都 best-effort（失败静默忽略，返回 nil）。
  2. 删 `/usr/bin/nginx` 软链（`os.ErrNotExist` 忽略）。
  3. 删整个 `/usr/local/nginx`（`os.RemoveAll`）。
  4. 删源码目录 `/data/soft/nginx-<版本>`（清理失败仅告警，不影响结果）。
  - 记录文件位于安装前缀内，删前缀即一并删除，无需单独处理。
- `nginxUninstallHandler`：POST /api/nginx/uninstall，复用「同一时刻一个 running 任务」
  互斥检查，复用 `GET /api/nginx/install/status` 轮询（snapshot 已补 `Action` 字段）。
- **把 `installPrefix`/`sourceDir` 从 const 改成 var**（默认仍是 /usr/local/nginx、
  /data/soft），以便单测临时重定向到 t.TempDir() 验证卸载范围，避免误删真实系统。
- 前端：在 `installed` 列 `a-popconfirm`（危险操作二次确认，ok-button 红色）加「卸载」按钮；
  新增独立 uninstall 弹窗（与 install 弹窗平行），同样 2 秒轮询日志、成功后自动 detect()。
  卸载按钮在 `installRunning || uninstallRunning` 时禁用。

### 后端：站点配置 API（server/main.go）

- `GET /api/nginx/sites`：读 config.d 下 *.conf，parseSiteConf 提取
  server_name/listen/root；返回 supported + nginxInstalled + configDir + sites。
  未安装 Nginx 时 nginxInstalled=false、sites=[]（前端提示先去安装页）。
- `POST /api/nginx/sites/create`：renderSiteConf 生成 server 块，sanitizeSiteFile
  转文件名（防路径穿越），同名不覆盖。
- `POST /api/nginx/sites/update`：按 file 定位，域名变更换文件名（先写新后删旧）。
- `POST /api/nginx/sites/delete`：删文件（filepath.Base 防穿越）。
- `POST /api/nginx/reload`：先 `nginx -t` 校验，通过则 `nginx -s reload`，
  未运行则直接启动；返回 {ok, action:'reload'|'start', output}。
- nginxBin() 优先 /usr/bin/nginx 软链，回退安装前缀二进制。
